① Agentes e Ferramentas: Fazer a IA agir, não só responder

Agente: Sistema com LLM que decide ações e usa ferramentas para cumprir uma tarefa.

Function calling: O modelo escolhe a função e gera os parâmetros em JSON => o sistema executa e devolve o resultado.

Fluxo: Cadastro das funções → análise da pergunta → geração da chamada → execução e resposta.

Definição de função: Nome, descrição e parâmetros (tipo e obrigatoriedade). Ideia-chave: bem descrita = chamada precisa.

Framework de orquestração: Organiza agentes, ferramentas, memória e execução. (Ex: LangChain, AutoGen)

Orquestrador (manager): Decompõe a tarefa e delega aos agentes especializados (executores), pelo significado e não por palavra-chave.

Handoff: A saída de um agente vira a entrada do próximo, levando contexto suficiente.

Pipeline: Etapas em sequência ou em paralelo. Ideia-chave: dividir em etapas facilita achar a falha (rastreabilidade).

② Planejamento Multiagente: Começar pelo problema, não pela tecnologia

Definição do problema: Quem é o usuário, qual a dificuldade e qual resultado se espera.

Quando usar IA generativa: Linguagem natural e respostas variadas. Regras fixas (CPF, impostos, somas) => código comum.

Requisito funcional: O que o sistema faz. (Ex: responder dúvidas do aluno)

Requisito não funcional: Como o sistema faz: desempenho, segurança, disponibilidade.

Critério de sucesso e MVP: Meta mensurável + produto mínimo viável. Ideia-chave: começar pequeno.

Sistema multiagente: Divide o problema em subtarefas, cada uma com um agente especialista (papel, ferramentas, entrega).

Orquestrador: Decompõe, delega, repassa contexto e consolida. Coordena, não faz tudo!

Diagrama de fluxo de dados: Mostra o caminho da informação => solicitação do aluno → agentes e ferramentas → resposta.

③ Código dos Agentes: Preparar o ambiente e dar conhecimento ao agente

Ambiente virtual (venv): Isola as bibliotecas de cada projeto e evita conflito de versões. (Ex: python -m venv .venv)

requirements.txt: Lista as dependências e versões. ModuleNotFoundError => biblioteca faltando ou ambiente errado.

Chave de API: Credencial secreta. Fica no .env (listado no .gitignore), nunca no GitHub.

Estrutura de pastas: Separar código, dados, notebooks e configuração.

Agente por regras: Entrada → regras (if/elif/else) → saída. Organizado em classe e método responder().

Limitação: O agente por regras não entende a pergunta e falha no que não foi previsto.

RAG (Geração aumentada por recuperação): Busca documentos relacionados antes de responder. (Ex: banco vetorial Chroma)

Memória de curto prazo: Guarda o histórico da conversa atual. Ideia-chave: memória = conversa; RAG = documentos.

④ Orquestração e Git: Coordenar os agentes e versionar o código

Orquestração: Coordenar quem faz, quando entra e como a informação circula.

Orquestrador = maestro: Distribui tarefas, gerencia o fluxo, trata falhas e integra os resultados.

Fluxo de agentes: Entrada → análise → resposta → resultado final. (Ex: função orquestrador())

Full-stack: A orquestração liga interface, back-end, APIs e agentes.

Tool (ferramenta externa): Usada quando a tarefa exige algo fora da conversa: dados reais ou uma ação. (Ex: API ViaCEP)

Fluxo com tool: Usuário → agente → API externa → agente → resposta.

Git: Branch isola, commit registra, merge integra.

Fluxo seguro: Correção em uma branch => testar e revisar => só depois merge na main.

⑤ Testes e Refinamento: Testar antes de confiar

Testar: Verificar se o agente realmente funciona na prática: resposta clara, útil, coerente e estável.

Teste de usabilidade: Foco na experiência do usuário => resposta clara, fácil de entender e que faz sentido no contexto.

Teste de confiabilidade: Foco na informação correta => resposta consistente, sem contradições e sem invenções.

Teste baseado em script: Roteiro planejado: pergunta, comportamento esperado (gabarito), pontos a observar e forma de registro.

Fluxo do teste: Pergunta → comportamento esperado → observação → registro.

O que observar: Entendeu a pergunta, respondeu ao pedido, manteve a lógica e trouxe informação confiável. Ideia-chave: resposta bem escrita também pode estar errada.

Bug x Alucinação: Bug = erro de funcionamento. Alucinação = resposta inventada, sem base confiável.

Registrar e ajustar: Registra prompt, resposta, problema e evidência => ajusta prompt, parâmetros, contexto e instruções.

Melhoria contínua: Testar → registrar → ajustar → testar novamente.

⑥ Deploy e Mercado: Do projeto escolar ao produto real

Projeto pronto para o mercado: Não basta rodar no PC do desenvolvedor: precisa ser instalado, usado e apresentado.

Critérios: Funcionamento sem erros, implantação simples, organização (arquivos, banco, documentação) e apresentação. (Ex: sistema de agendamento de uma clínica)

Portabilidade: Onde o software pode funcionar => diferentes ambientes e dispositivos. (Ex: Nubank com Flutter: um código para Android e iOS)

Escalabilidade: O quanto o sistema cresce (mais usuários, mais funções) sem perder desempenho nem estourar o custo.

Conteinerizar: Empacotar a aplicação com tudo o que ela precisa: bibliotecas, dependências e configurações.

Benefícios do contêiner: Evita diferença entre ambientes, reduz configuração manual e facilita testes e deploy. Ideia-chave: roda igual em qualquer lugar.

Fluxo Docker: Aplicação → Dockerfile → imagem (docker build) → contêiner (docker run) → cloud (deploy).

Dockerfile = receita: FROM imagem base, WORKDIR pasta, COPY arquivos, RUN instala dependências, CMD executa.

Pitch: Mostrar o que a solução faz, qual problema resolve e o que foi aprendido, com clareza e confiança.
